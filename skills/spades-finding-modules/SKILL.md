# Finding and combining SpaDES modules

Most SpaDES work starts by assembling modules other people wrote, not by writing one.
This skill covers where to find them and how to tell whether a set of them will run
together.

## The catalogue

The list of known public modules is the
[Modules list](https://github.com/PredictiveEcology/SpaDES-modules/wiki/Modules-list)
wiki page in `PredictiveEcology/SpaDES-modules`: ~280 modules in 17 subject sections,
each linked to its repository and credited to its authors.

**Read the live page. Do not copy it into an answer as a cached list.** It is
regenerated by `tools/update-wiki.py` in that repo from a scan of commit activity and
cross-repository usage, so the status markers are only true as of the date in the page
header. A remembered module list goes stale quietly, and the expensive error is telling
someone a module is maintained when it has been archived.

Sections, in the order they appear: LandR Biomass vegetation dynamics, fire, forest
carbon, harvesting and forest management, CASTOR, insects and forest health, caribou,
birds, other wildlife, human disturbance and land use, climate and weather data, study
areas and project setup, summaries and reporting, teaching examples, retired, and
modules maintained elsewhere.

### Reading the markers

Status:

| | meaning |
|---|---|
| 🟢 | active — changed in the last 12 months on its live branch |
| 🔵 | stable — no recent changes, but a project active in the last 18 months still uses it |
| ⚪ | quiet — no recent changes and no public project known to use it |
| 🗄 | repository archived (read-only) |
| ⚠ | still uses the retired `raster`/`sp` packages |
| ·N | number of public projects that list this module |

What the module does: 📥 data, 🎯 parameterizing, ⏩ prediction, 🔁 simulation,
📋 summary, 🔌 translator, 📚 library. Most modules carry more than one.

Two markers are easy to misread. **⚪ does not mean broken** — it means nobody public
is using it, which is common for a module written for one study. **🗄 plus a ·N above
zero** means an archived module that live projects still call; those cannot simply be
replaced, the callers have to migrate first. The Retired section names the successor
for each where one exists.

## Getting the modules

You do not download modules by hand. `setupProject()` fetches them and the R packages
they need:

```r
out <- SpaDES.project::setupProject(
  paths = list(projectPath = "~/myProject"),
  modules = c(
    "PredictiveEcology/Biomass_speciesData@main",
    "PredictiveEcology/Biomass_borealDataPrep@main",
    "PredictiveEcology/Biomass_core@main"
  ),
  times = list(start = 2011, end = 2031)
)
simOut <- SpaDES.core::simInitAndSpades2(out)
```

The part after `@` is the branch; leaving it off takes the default. Some repositories
hold several modules in folders, so point at the folder:

```r
modules = file.path("PredictiveEcology/scfm@development/modules",
                    c("scfmLandcoverInit", "scfmRegime", "scfmDriver",
                      "scfmIgnition", "scfmEscape", "scfmSpread"))
```

Within PredictiveEcology, development happens on `development` branches; `@main` gives
you the released state. Pick one and be consistent across the set — a project mixing
`@main` modules with `@development` ones is a common source of version-floor failures.

## What "compatible" means

The catalogue groups modules by subject. Subject is a hint, not a contract. Three
things decide whether a set actually runs.

**1. Object names match.** Modules communicate only through named objects in the
`simList`: one module's `createsOutput` must be another's `expectsInput`. That is the
whole interface. To check a pair, read their `defineModule()` metadata and compare the
`inputObjects` and `outputObjects` blocks — do not infer it from the module names or
from their being in the same wiki section.

Each family has a shared data convention underneath those names: `cohortData` plus
`pixelGroupMap` for LandR Biomass, `rstCurrentBurn` for fire modules, `studyArea` and
`rasterToMatch` almost everywhere. Modules within a family usually compose. Across
families you often need a translator (🔌) or a data-prep module (📥) in between.

**2. Nothing unsatisfied is left over.** After picking a set, list every
`expectsInput` that no module in the set creates. Each one must either have a sensible
default in that module's `.inputObjects`, or be supplied by you through
`setupProject(objects = ...)`. Unsatisfied inputs are the usual reason a first
`simInit()` fails.

**3. The stack is consistent.** A ⚠ module uses `raster`/`sp`, which are retired. In a
project built on `terra` it will need porting before it runs — a real piece of work,
not a warning to ignore. And `reqdPkgs` entries can carry version floors like
`PredictiveEcology/LandR@development (>= 1.2.0.9024)`; two modules in one project can
name incompatible floors, which fails at install time, before any ecological question
arises.

## Traps when assembling a set

- **Fit/predict pairs.** fireSense is organised as `*Fit` and `*Predict` per process
  (ignition, escape, spread). A Predict module without its Fit, or without the fitted
  object supplied, is not a working set.
- **Data prep is not optional.** `Biomass_core` needs initial `cohortData`; that comes
  from `Biomass_borealDataPrep` (or equivalent), which in turn needs species layers
  from `Biomass_speciesData`. The typical chain is data prep → engine → summary.
- **Succession and disturbance interact.** A regeneration module's behaviour depends on
  what kind of disturbance precedes it — stand-replacing versus partial mortality give
  different cohort structures. Check which one the set implies.
- **·N is a decent proxy for "this has been run by someone recently".** A module with
  a high count and 🟢 has been exercised; a ⚪ module with no count may work perfectly
  and may never have been run outside its author's machine.

## Procedure for a new project

1. Find candidates in the wiki section for the subject. Note markers.
2. Read each candidate's `defineModule()` — `description`, `keywords`,
   `inputObjects`, `outputObjects`, `reqdPkgs`. The `<Module>.Rmd` manual is the longer
   version.
3. Write down the object graph: who creates each shared object, who consumes it, what
   is left unsatisfied.
4. Resolve the leftovers — add a data-prep module, or plan to supply the object.
5. Check for ⚠ modules and for conflicting version floors.
6. `setupProject()` with a short `times` range and a small study area, and run it once
   before scaling up.

Steps 3 and 5 are where sets fail, and both are cheap compared with debugging a failed
run.
