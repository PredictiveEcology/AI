# LandR accessory package maintenance

The ecosystem has three R packages (each its own folder under `~/GitHub/LandR`):

- `LandR/` — core utilities. Imports `SpaDES.core`, `SpaDES.tools`, `data.table`, `raster`,
  `reproducible`, `sf`, `sp`, and more. roxygen2 docs; **no testthat suite yet**.
- `LandR.CS/` — climate-sensitive growth/mortality; small (2 R files).
- `fireSenseUtils/` — fire utilities; has `tests/testthat/`.

Each is a standard R package: `DESCRIPTION`, `NAMESPACE`, `R/`, `man/`, `README.md`,
`NEWS.md`. NAMESPACE and `man/*.Rd` are **generated by roxygen2** — never hand-edit them.

## devtools workflow

Work from the package directory. Typical loop:

```r
library(devtools)
document("LandR")     # regenerate NAMESPACE and man/ from roxygen2 blocks
load_all("LandR")     # load for interactive testing
test("LandR")         # run testthat suite
check("LandR")        # full R CMD check
```

## DESCRIPTION and dependencies

- Add new hard dependencies under `Imports:`; test-only deps under `Suggests:`.
- GitHub deps are pinned in `Remotes:` (e.g. `PredictiveEcology/reproducible@development`).
- Keep `Language: en-CA`. `RoxygenNote` reflects the roxygen2 version used to build.
- If you import a function, add `@importFrom pkg fun` in a roxygen block (do not edit
  NAMESPACE directly), then `document()`.

## Adding or changing exported functions

1. Write the function in `R/` with a roxygen2 block including `@export`
   (see `code-documentation`).
2. `document()` to update NAMESPACE + `man/`.
3. Add/adjust tests under `tests/testthat/`.
4. `test()` then `check()`.

## Versioning and NEWS

- Bump `Version` in `DESCRIPTION` (packages use a 4-part dev scheme, e.g. `0.0.1.9005`;
  increment the 4th component for development changes).
- Add a matching `NEWS.md` entry describing user-facing changes.
- Modules pin package versions in their `reqdPkgs` (e.g.
  `PredictiveEcology/LandR@development (>= 1.1.0.9006)`); when you raise a package's
  minimum required version, check whether dependent modules need their pins updated.

### Module version alignment across the ecosystem

This applies to LandR **modules** (their own `version` field in `defineModule()`), not just
the accessory packages above — the same alignment concern applies to package versions too.

- **Major and minor module versions need to stay aligned across the modules in a given
  workflow/pipeline** (e.g. the `Biomass_*` family, or a `fireSense_*` fit/predict pair).
  A patch/dev bump to one module can require bumping the `version` of sibling modules that
  did not themselves change, purely so the set advertises a consistent major.minor line.
- **Never bump an unchanged module's version without first checking compatibility** between
  it and the module(s) that did change. A version bump is a claim about compatibility, not
  just a label — bumping it without verifying compatibility is misleading.
- **Module integration tests are the primary tool for this check** (see the `testing`
  skill's integration-test guidance): run the relevant multi-module chain
  (`simInit()`/`spades()` across the modules involved) before bumping, and again after, to
  confirm the updated and not-yet-updated modules still interoperate through their shared
  `simList` objects.
- If a compatibility problem turns up, **stop and flag it to the user** rather than bumping
  anyway — this is a decision about the ecosystem's release consistency, not a mechanical
  version-string edit.

## Notes

- `utils::globalVariables(...)` calls at the top of some `R/` files silence
  `data.table` NSE `R CMD check` NOTES — keep them in sync when you add new column names.
- `LandR` currently has no tests; adding testthat scaffolding
  (`usethis::use_testthat()`) is a reasonable improvement when asked.
